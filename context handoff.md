## Product goal

Build a simple dashboard for viewing Claude and Codex chat history across multiple projects and codebases. The interface should feel like one page of compact terminal windows. Keep the visual language minimal and monochrome.

## Current design direction

- Light gray page background, white agent cards, black primary text, and muted gray terminal output.
- Compact, terminal-inspired cards arranged in a responsive grid.
- Working and Completed each use a two-column card grid. On phones the status sections stack vertically, while compact cards keep a 2×2 view so up to four agents remain visible together.
- The project controls and floating agent windows reflow for narrow or short screens; open windows clamp back into the viewport when it is resized.
- Hover gives a subtle lift and reveals an open hint.
- Selecting a card opens a focused terminal dialog where the user can enter and send a follow-up prompt.
- The dialog shows the complete conversation history, tool calls and results, and a Details tab with session metadata.
- Clicking outside the dialog or pressing Escape closes it.
- The dialog, terminal output, prompt field, and buttons use the same light palette.
- Keep the UI simple; avoid adding decoration or extra explanatory hero copy.

## Chat discovery and filtering

- No chats are read or displayed until at least one folder is selected with the folder picker.
- Selected folder paths are persisted in `imported-projects.json`; removing a folder stops showing its chats.
- The feed includes all Claude and Codex sessions whose launch or turn working directory, or recorded tool working directory, is the selected folder or one of its descendants, including chats older than 14 days.
- Project filters are multi-select and narrow the visible agents.
- The All filter selects every project.
- Selecting an additional folder resets the project filters to include its related chats; new projects under selected folders are selected automatically.

## Current implementation

- `server.js` (plain Node, no dependencies) is adapter-based: each adapter knows how to find one agent CLI's session files and parse them into a common shape, tagged with `agentType`. It exposes `GET /api/agents` as the live data source and also serves `index.html` as static content. Run with `node server.js` (port 4178, override with `PORT`).
- Adapters implemented:
  - **claude** — `~/.claude/projects/<encoded-cwd>/<session>.jsonl`. `cwd`/`gitBranch` are read from the transcript, anchored on the *first* occurrence for the session launch location; observed turn `cwd` values are also used when matching a chat to selected folders.
  - **codex** — `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`. Different event schema (`session_meta`, `turn_context`, `response_item`, `event_msg`); launch `cwd` comes from `session_meta.payload.cwd`; session-to-folder matching also checks turn contexts and explicit tool-call working directories so sessions started in a shell's home folder still appear under the repo they actually work in. Last prompt/response comes from `response_item` messages with a fallback to `event_msg` `task_complete.last_agent_message`. Codex transcripts don't carry a git branch, so it's resolved by shelling out to `git -C <cwd> rev-parse --abbrev-ref HEAD` (cached per cwd for the request).
  - To add another agent CLI (Cursor, Gemini, Copilot, etc.): add a `listXAgents()` that returns agent objects via the shared `finalizeAgent()` helper, then push it into the `ADAPTERS` array. Quick disk check found Cursor/Gemini/Copilot keep conversation history in app-internal SQLite/state, not plain per-session transcript files, so they'd need real reverse-engineering before wiring up — skipped for now.
  - `GET /api/agents/:id/files` returns file paths recorded by session edits: Claude `Edit`/`MultiEdit`/`Write`, Codex `apply_patch`, and common shell output forms such as `curl -o`, `tee`, and redirection. The transcript is scanned as a stream and appended content is scanned incrementally, so large sessions do not need to be loaded into memory again on each refresh. `POST /api/agents/:id/open-file` opens a listed existing file in Zed (or the app named by `AGENTMANAGER_EDITOR`).
  - Session transcripts can be enormous — one Codex rollout on this machine is 1.07GB, several others are 70-500MB — and the dashboard was reading+fully JSON-parsing every session file on *every 4s poll*, which is what made initial load (and everything after) painfully slow. Fixed with `getListContent()`: reads only bounded head/tail chunks (`HEAD_BYTES`=64KB, `TAIL_BYTES`=512KB) via `fs.readSync` at explicit byte offsets — enough to find the first `cwd`/branch and the last prompt/response — and caches the parsed result per file keyed by `(mtimeMs, size)`, so completed sessions (the overwhelming majority) are never re-read once cached. Cut `/api/agents` from reading ~2GB per request to ~10-20ms.
- One session file = one chat card. All dates are included. State follows transcript lifecycle markers when present: Claude assistant turn endings/duration markers and Codex `task_started`, `task_complete`, and `turn_aborted`. The 15s recency heuristic is only a fallback when no lifecycle marker is available. A real AgentManager pending approval overrides this to Waiting. The dashboard refreshes agent state every second.
- The Completed column shows its two most recently active chats by default, with a View more / Show less control.
- The Working column includes approval-blocked sessions; those cards flash red and show Allow/Deny controls. Working cards keep a stable order by session start time as output arrives. Completed remains sorted by latest activity.
- `index.html` has no hardcoded agent data — it fetches `/api/agents` on load and polls every second, keyed by session `id` so an open detail dialog survives a refresh. Agent titles are derived from the first user prompt in each transcript so follow-ups keep the same title; the latest prompt remains in the preview. Cards use a Claude starburst mark with a subtle orange tint and the supplied Codex image (`assets/codex-agent-icon.png`) with a soft gray tint to identify each provider. The global top header strip was removed; workspace filters and agent counts remain in the board area.
- The reprompt composer resumes the exact selected Claude/Codex session ID. Additional prompts submitted while a follow-up is running are queued per session and resumed sequentially against that same ID; they do not create new session cards.
- The detail dialog has Chat, Details, and Files tabs. Chat fetches the transcript in 40-message pages; “Load earlier messages” walks back through large transcripts in bounded byte chunks. User/assistant messages share the same bubbles across providers; tool calls and results use matching collapsed rows, with Codex custom tool events normalized alongside function calls. Image placeholders and timestamps are shown; model reasoning blocks remain hidden. Details shows session metadata. Files refreshes while open, lists paths recorded in the session's edit/write calls, and opens an existing file in Zed; set `AGENTMANAGER_EDITOR` to choose another macOS app.
- The old fake "New agent" button was removed — it fabricated a sample agent, which contradicted "no hardcoded data."
- Working cards have a light yellow background, Completed cards have a light green background, and approval-blocked cards flash red. The Working/Completed status dots also use their matching colors.
- **Sending is now real.** `POST /api/agents/:id/send` (fire-and-forget, per your call) spawns a headless resume of the exact session and lets it run detached. The selected permission mode is applied to each dashboard-launched follow-up:
  - **Claude**: `claude --print --resume=<id> --permission-mode=<mode> --setting-sources project,local --settings '<inline hooks JSON>' "<message>"`. `--setting-sources project,local` deliberately drops the `user` source so this per-invocation call never loads `~/.claude/settings.json` (where Vibe Island's global hooks live) — it only gets the `PreToolUse` hook we inject inline, isolated to this one subprocess. `default` is sent as Claude's `manual`; Auto, Accept edits, Full auto, and Plan use their matching Claude permission-mode names. Resuming by ID restores the session's own cwd automatically; we still pass `cwd` on the spawn for good measure.
  - **Codex**: `codex exec resume -c sandbox_mode=... -c approval_policy=... <id> "<message>" --skip-git-repo-check`, cwd set via Node's own `spawn({cwd})`. Auto, Manual approval, and Accept edits keep the `workspace-write` sandbox with `on-request`; AgentManager's hook applies the per-tool approval behavior. Plan uses `read-only` with approvals disabled. Full auto uses Codex's dangerous full-access flag. Codex has no per-invocation hook flag, so this also relies on the global `~/.codex/hooks.json` entry described below.
- **Approval queue, built into the dashboard (not just a passive reflection of Vibe Island).** You already had Vibe Island wired into both CLIs' `PermissionRequest`/`PreToolUse` hooks globally (`/Applications/Vibe Island.app`, via `~/.vibe-island/bin/vibe-island-bridge` — found this mid-build, it's why "needs approval" wasn't a build-from-scratch problem). You asked for dashboard-sent prompts specifically to get their own approve/deny UI instead of going through Vibe Island, so:
  - `approval-hook.js` (new file) is a single script used two different ways. For **Claude** it's injected only on the subprocess above — never installed globally, so every other Claude session keeps using Vibe Island untouched. For **Codex** there's no per-invocation option, so it's added as a *new, additive* `PreToolUse` entry (matcher `"*"`) in the real global `~/.codex/hooks.json`, alongside your existing `graphify`/Vibe Island entries — nothing existing was removed. The script checks `AGENTMANAGER_SESSION_ID` (only set on subprocesses this dashboard spawns): if unset, it execs the existing `vibe-island-bridge` with the hook's stdin/stdout passed straight through, so every normal interactive Codex session behaves exactly as before. If set, it registers the request with AgentManager's own server and blocks.
  - Flow: hook reads the tool-call JSON off stdin → `POST /api/approvals` (in-memory queue, `{id, sessionId, agentType, toolName, toolInput, cwd, status}`) → polls `GET /api/approvals/:id` every second for up to ~280s → prints `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow"|"deny",...}}` and exits 0/2 accordingly. Verified end-to-end against the real running server (not just unit logic): registered, approved, and denied paths all produced the correct exit code and JSON.
  - `getAgents()` cross-references `pendingApprovals` by session id and attaches `pendingApproval: {id, toolName, toolInput}` when a real tool call is blocked. The Working card flashes red and shows Allow/Deny controls; the open dialog's approval banner also reads this field. `POST /api/approvals/:id/decide` handles those buttons.
  - **Still needed on your end, one-time**: Codex requires a trust hash per hook entry in `~/.codex/config.toml` before it'll actually run a hook non-interactively, and I deliberately did *not* use `--dangerously-bypass-hook-trust` to skip that (declined by the auto-mode classifier when I tried it during testing, correctly — that flag wasn't something you'd explicitly named, and bypassing a trust check isn't something to do quietly). Run `codex` interactively once in any trusted project and accept the trust prompt for the new hook entry — after that, headless dashboard-sent Codex prompts will route through the approval queue correctly. Until you do that, Codex sends may hang or fail at the first tool call.
  - **Confidence note**: Claude's hook contract (stdin/stdout shape, `--setting-sources`/`--settings` isolation) was verified empirically against the real installed CLI (v2.1.204) on this machine, not just docs — I don't fully trust vendor-flag claims from a research pass alone anymore after one agent fabricated a `--permission-prompt-tool` flag and an `"http"` hook type that don't exist in this binary. Codex's side is best-effort: the `tool_input` field name was confirmed real (by reading your already-working `graphify hook-check` script, which parses live Codex `PreToolUse` input), but I couldn't run a real `codex exec resume` against the live global hook without either the trust bypass (declined) or spending real API calls against a throwaway session, so treat Codex's exact output contract as unconfirmed until your first real send either works or doesn't.
- **Mode badge now reflects the session's real state, not just the dashboard's own toggle.** The bug you flagged — a card showing "manual approval" for a session you'd actually put in auto mode — was because `agent.mode` was *only* ever the dashboard's own independently-stored override (`agentModes` map, defaulting to `'default'` until someone touches the dropdown), never anything read from the live session itself. Fixed by parsing the session's actual recorded mode straight from its transcript:
  - **Claude** writes `permissionMode` onto every `"type":"user"` entry (anchored on the *last* occurrence, since this tracks live state, not launch state) — real values seen in your own transcripts: `default`, `auto`, `acceptEdits`. `manual` (Claude's literal "nothing special" value) normalizes to `null`/no-badge.
  - **Codex** records `turn_context.approval_policy` and `sandbox_policy.type` per turn. `workspace-write` with `on-request` or the observed granular policy maps to Auto; `read-only` maps to Plan; `danger-full-access` maps to Full auto. These correspond to Codex's separate sandbox and approval controls. Legacy stored `default` mode values no longer mask the transcript's live detected mode; selecting Manual approval stores a distinct explicit override.
  - Both land in `agent.detectedMode`. An explicit dashboard override wins for the effective mode, badge, and dropdown preselect. Legacy stored `default` values defer to the detected mode; otherwise the effective fallback is Manual approval.
- **Slash commands — tested for real, not assumed:**
  - **Claude**: already works today with zero code changes, because `sendPromptToAgent` just forwards your literal message text as the `-p` prompt argument, and Claude Code's slash-command/skill parsing runs on that same input in headless mode too. Verified with two real calls: `claude --print "/help"` correctly recognized it as a command attempt (replied "isn't available in this environment" — the *specific*, structured response for a UI-only command, not a conversational guess), and `claude --print "/code-review --help"` correctly identified the real skill, its real argument grammar, and that `--help` isn't valid for it.
